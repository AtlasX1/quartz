---

## 1) 🧱 SOLID Principles

**Ціль:** створювати підтримуваний, розширюваний та чистий код.

- **S — Single Responsibility Principle:**  
  Кожен клас або модуль повинен мати лише одну причину для зміни.  
  → *Зменшує зв’язність, полегшує тестування й підтримку.*

- **O — Open/Closed Principle:**  
  Класи мають бути відкритими для розширення, але закритими для модифікації.  
  → *Використання інтерфейсів, абстрактних класів і DI.*

- **L — Liskov Substitution Principle:**  
  Об’єкти підкласів повинні бути взаємозамінними з об’єктами батьківських класів.  
  → *Сумісність поведінки без порушення інваріантів.*

- **I — Interface Segregation Principle:**  
  Краще багато вузьких інтерфейсів, ніж один великий.  
  → *Зменшує кількість непотрібних залежностей.*

- **D — Dependency Inversion Principle:**  
  Залежності мають будуватись від абстракцій, а не від конкретних реалізацій.  
  → *Основи DI/IoC контейнерів (наприклад, у NestJS або Spring).*

## 2) 🧩 Design Patterns (GoF)

**Ціль:** ефективно застосовувати патерни для розв’язання типових проблем.

### Creational Patterns
- **Factory Method / Abstract Factory:** інкапсуляція створення об’єктів.
- **Builder:** покрокове створення складних об’єктів.
- **Singleton:** контрольована глобальна точка доступу (з обережністю).

### Structural Patterns
- **Adapter:** узгодження несумісних інтерфейсів.
- **Decorator:** динамічне розширення поведінки без зміни коду.
- **Composite:** деревоподібні структури з єдиним інтерфейсом.
- **Proxy:** контроль доступу або ліниве завантаження.

### Behavioral Patterns
- **Observer:** реактивна модель публікації/підписки.
- **Strategy:** динамічна заміна алгоритмів.
- **Command:** інкапсуляція дії як об’єкта.
- **State:** поведінка залежно від стану.
- **Mediator:** централізована координація між компонентами.

> **Практика:** застосування цих патернів у фронтенді (React hooks, context, redux), бекенді (NestJS, Node.js, Spring), або DDD.

## 3) 🧭 Domain-Driven Design (DDD)

**Ціль:** узгодити технічну та бізнес-логіку системи через спільну мову та структуру.

- **Ubiquitous Language:** єдина мова між розробниками та експертами домену.
- **Entities / Value Objects:** ідентичність проти значення.
- **Aggregates:** групування об’єктів із одним коренем (aggregate root).
- **Repositories:** абстракція доступу до даних.
- **Services:** поведінка, яка не належить конкретному об’єкту.
- **Bounded Contexts:** ізольовані області логіки.
- **Context Mapping:** інтеграція між контекстами через Anticorruption Layer, Shared Kernel тощо.
- **Event Storming:** візуалізація доменних подій і взаємозв’язків.

## 4) 🏗️ Architectural Styles (Monolith vs Microservices)

**Ціль:** розуміти архітектурні компроміси між монолітом і мікросервісами.

### Monolithic Architecture
- Простота розгортання, менше мережевих витрат.
- Легше почати, але складно масштабувати команду й кодову базу.
- Єдина БД → спільні транзакції → тісна зв’язність.

### Microservices Architecture
- Декомпозиція системи на незалежні сервіси.
- Можливість масштабувати частини незалежно.
- Незалежні деплоя та CI/CD.
- Виклики: **комунікація, консистентність, спостережуваність.**

> **Trade-offs:** моноліт легше валідувати й розгорнути; мікросервіси краще підходять для еволюційних систем з великою командою.

## 5) 🌐 RESTful API Design

**Ціль:** проєктувати API з урахуванням стандартів, стабільності та передбачуваності.

- **Statelessness:** кожен запит не залежить від попереднього.
- **HTTP methods:** GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS.
- **Status codes:** 2xx, 4xx, 5xx — узгоджені відповіді.
- **Idempotency:** повторний запит не змінює стан.
- **Pagination, filtering, sorting, versioning.**
- **HATEOAS, resource representation, content negotiation.**
- **Errors:** стандартизований формат (`code`, `message`, `details`).
- **Security:** HTTPS, CORS, rate limiting, JWT/OAuth2.
- **Documentation:** OpenAPI/Swagger, Postman Collections.

---

## 6) ⚙️ Microservices Architecture

**Ціль:** створювати масштабовані, незалежні сервіси з продуманою взаємодією.

- **Комунікація:** REST, gRPC, Message Bus, GraphQL Federation.
- **Service Discovery:** Consul, Eureka, DNS, API Gateway.
- **Fault tolerance:** retries, backoff, timeout, circuit breaker.
- **Data ownership:** database-per-service, eventual consistency.
- **Resilience patterns:** bulkhead, throttling, retry, fallback.
- **Observability:** logs, metrics, tracing (OpenTelemetry, Jaeger).
- **Deployment:** containers, CI/CD, Kubernetes.
- **Scalability:** горизонтальне масштабування, autoscaling, load balancing.

---

## 7) 🧩 Microservices Patterns

**Ціль:** знати ключові патерни для стійких розподілених систем.

- **API Gateway:** централізований вхід для всіх запитів.
- **Circuit Breaker:** запобігання каскадним збоям.
- **Event Sourcing:** стан як послідовність подій.
- **CQRS (Command Query Responsibility Segregation):** розділення команд і читань.
- **Saga:** керування довгими транзакціями через оркестрацію або хореографію.
- **Bulkhead:** ізоляція частин системи для запобігання колапсу.
- **Retry & Backoff:** повтори з експоненціальним інтервалом.
- **Strangler Fig:** поступова заміна моноліту.
- **Database-per-service:** розділення сховищ для незалежності.

---

## 8) 🔄 Asynchronous Architecture (Event-Driven)

**Ціль:** створювати масштабовані та реактивні системи.

- **Подійно-орієнтована архітектура (EDA):**
  - Сервіси реагують на події замість прямих викликів.
  - Зменшення зв’язності, покращення масштабування.
- **Брокери повідомлень:** Kafka, RabbitMQ, NATS, AWS SNS/SQS.
- **Event Bus / Event Store:** централізоване збереження подій.
- **Event sourcing:** зберігання стану через історію подій.
- **Outbox Pattern / Transactional Events:** надійна доставка повідомлень.
- **Real-time обробка:** Streams, CDC (Change Data Capture).
- **Fault tolerance:** replay, deduplication, idempotency.
- **Приклади:** аудит, нотифікації, аналітика в реальному часі.
