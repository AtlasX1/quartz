# Масиви та структури даних: Теоретичне занурення

> **Аудиторія:** L4 інженери | **Фокус:** Математичні основи, принципи дизайну, фундаментальні компроміси

## 🎯 Концептуальний огляд

Структури даних **кодують взаємозв'язок між часом та простором**. Вони є фундаментальними математичними об'єктами з доказуваними властивостями, а не просто програмістськими зручностями.

**Основна теза:** Кожна структура даних являє собою **точку на поверхні компромісу** між:
1. **Складність доступу:** Час для пошуку елементу
2. **Складність модифікації:** Час для вставки/видалення
3. **Просторова складність:** Витрата пам'яті
4. **Ефективність кешу:** Локальність посилань на сучасному обладнанні

Немає **універсально оптимальної структури**—лише оптимальні вибори для конкретних шаблонів доступу та обмежень.

На L4 рівні ви повинні розуміти:
- **Математичні нижні межі** для різних задач
- **Інформаційно-теоретичні межи** обчислень
- **Ієрархія пам'яті** та чому поведінка кешу домінує у реальній продуктивності
- **Фундаментальні компроміси** в різних представленнях

## 📍 1. Динамічні масиви: Амортизований аналіз

### 1.1 Фундаментальна задача

**Питання:** Як підтримати **O(1) push()** на масиві необмеженого розміру при обмеженості фізичної пам'яті?

**Наївний підхід:** Виділити точно n елементів для n елементів.
- Перша push: виділити 1 байт
- Друга push: виділити 2 байти, скопіювати існуючі дані
- n-та push: виділити n байтів, скопіювати існуючі дані

**Загальна вартість:** $1 + 2 + 3 + \ldots + n = \frac{n(n+1)}{2} = O(n^2)$

Це катастрофально повільно. Потрібна краща стратегія.

### 1.2 Стратегія подвоєння

**Ключова ідея:** Замість виділення рівно n слотів, виділяємо $2^k$ слотів, де k зростає час від часу.

Коли ємність перевищена одним елементом:
- Стара ємність: $2^k$
- Нова ємність: $2^{k+1}$
- Вартість копіювання: $O(2^k)$

**Як часто ми перевиділяємо?**

Для n push операцій:
- Перевиділення відбувається при n = 1, 2, 4, 8, ..., $2^{\log_2 n}$
- Кількість перевиділень: $O(\log n)$

**Загальна вартість перевиділення:**
$$\sum_{i=0}^{\log_2 n} 2^i = 2^{\log_2 n + 1} - 1 \approx 2n$$

**Загальна вартість для n push операцій:** $n + 2n = O(n)$

**Амортизована вартість на push:** $\frac{O(n)}{n} = O(1)$ ✓

### 1.3 Амортизований аналіз: Формальне визначення

Нехай $T(n)$ = загальний час для n операцій.

$$\text{Амортизована вартість на операцію} = \frac{T(n)}{n}$$

**Для динамічних масивів з подвоєнням:**
$$T(n) = n \cdot O(1)_{\text{push}} + O(n)_{\text{перевиділення}} = O(n)$$

Отже: $\text{Амортизована} = \frac{O(n)}{n} = O(1)$

**Важливо:** Це не означає, що кожна push є O(1). Це означає:
- В середньому над n операціями: O(1) на операцію
- Окремі операції можуть бути O(n)

Це точно захоплюється амортизованою межею.

### 1.4 Оптимальний коефіцієнт зростання

Якщо ємність зростає на коефіцієнт $\alpha > 1$:
- Кількість перевиділень: $O(\log_\alpha n)$
- Загальна вартість перевиділення: $\sum_{i=0}^{\log_\alpha n} \alpha^i = O(n)$
- Витрачена пам'ять: $\alpha \cdot n - n = (\alpha - 1) \cdot n$

**Компроміс:**
- $\alpha = 1.1$: Багато перевиділень (накладні видатки), мінімальні витрати
- $\alpha = 2.0$: Мало перевиділень, 50% середня витрата
- $\alpha = 1.5$: Баланс між частотою та витратами (~25% витрата)

**Теоретичний оптимум:** $\alpha = \phi \approx 1.618$ (золотий переріз)

На практиці вибирають $\alpha = 1.5$ для хороших констант.

### 1.5 Інформаційно-теоретична перспектива

Дано n елементів, мінімальна кількість бітів для уникального ідентифікування одного:
$$\log_2(n) \text{ бітів}$$

Доступ до масиву досягає цієї оптимальності шляхом прямого обчислення адреси:
$$\text{адреса} = \text{база} + i \times \text{розмір\_елемента}$$

Жодна структура даних не може принципово робити краще ніж **O(1) випадковий доступ**—це інформаційно-теоретично оптимально.

### 1.6 Проблема ієрархії кешу

Сучасні процесори мають ієрархічну пам'ять:

| Рівень | Час доступу | Розмір | Застосування |
|-------|---|---|---|
| L1 Кеш | 4 цикли | 32 KB | Негайно |
| L2 Кеш | 12 циклів | 256 KB | Часто |
| L3 Кеш | 40 циклів | 8-20 MB | Робочий набір |
| DRAM | 200 циклів | 8-64 GB | Набір даних |
| Диск | 10,000,000 циклів | TB | Холодне сховище |

**Ключовий механізм: просторова локальність**

Коли ви отримуєте доступ до адреси пам'яті x, процесор завантажує **лінію кешу** (64 байти) що містить x та сусідні адреси.

**Ітерація масиву:**
1. Доступ до arr[0]: процесор завантажує байти 0-63 в кеш
2. Доступи до arr[1..7]: попадання в кеш (50× швидше)
3. Доступ до arr[8]: промах кешу, але prefetcher вже завантажив arr[8..15]

**Ітерація пов'язаного списку:**
1. Доступ до node[0]: процесор завантажує вузол за адресою пам'яті x
2. Доступ до node[0].next: нова випадкова адреса, **промах кешу**
3. Кожен обхід = промах кешу

**Практичний вплив:** Ітерація масиву ≈ **50× швидше** ніж пов'язаний список, навіть хоча обидва теоретично O(n).

Ця різниця **домінує реальною продуктивністю**, а не алгоритмічна складність.

### 1.7 Рідкі масиви: Адаптивне представлення

Коли масив рідкий (кілька елементів, багато порожніх місць), що відбувається?

**Рішення V8:** Адаптивне перемикання

- **Щільний режим**: індекси 0, 1, 2, 3, ... → суміжна пам'ять
- **Рідкий режим**: індекси {0, 10000} → перемикається на хеш-таблицю

Вартість рідкого масиву:
- Доступ: O(1) в середньому (хеш-таблиця)
- Простір: O(елементи), не O(макс_індекс)
- Ітерація: O(елементи), не O(макс_індекс)

**Фундаментальна межа:** Ви не можете одночасно досягти:
1. O(1) доступ для довільних індексів
2. O(1) простір для k заповнених елементів (k << макс_індекс)

Це **теорема**, а не деталь реалізації.

Варіанти:
- **Масив:** O(1) доступ, O(n) простір (де n = макс_індекс)
- **Хеш-таблиця:** O(1) середній доступ, O(k) простір (де k = заповнені елементи)
- **Дерево:** O(log k) доступ, O(k) простір

## 📍 2. Пов'язані списки: Теоретичне обґрунтування

### 2.1 Центральний компроміс

**Питання:** Чи можемо ми досягти **O(1) вставки на позиції k** без O(n) витрат простору?

**Часткова відповідь:** Так, якщо прийняти **O(k) час доступу** для досягнення позиції k.

Властивості пов'язаного списку:
| Операція | Час | Примітки |
|---|---|---|
| Доступ до елемента k | O(k) | Потрібно обійти k вказівників |
| Вставка після відомого вузла | O(1) | Просто оновити вказівники |
| Видалення відомого вузла (двосторонній) | O(1) | Однорядковий: O(n) для пошуку попередника |
| Простір на елемент | O(1) вказівники | Вища константа ніж масив |

**Коли цей компроміс раціональний:**
1. Вставка/видалення >> доступ за частотою
2. Часто у вас є прямі вказівники на позиції
3. Робота з незмінювальними/функціональними парадигмами

### 2.2 Чому поведінка кешу переважує пов'язані списки

**Модель зовнішної пам'яті (Aggarwal-Vitter):**

Визначимо вартість I/O як кількість передач блоків, де:
- M = розмір швидкої пам'яті (L1 кеш)
- B = розмір передачі блоку (лінія кешу = 64 байти)
- N = розмір задачі

**Вартість послідовного сканування:** $\frac{N}{B}$ передач

**Вартість випадкового доступу:** $N$ передач (без prefetching)

Для N = $10^9$ елементів, B = 64 байти:
- Сканування масиву: $\frac{10^9}{8} \approx 125M$ передач
- Обхід пов'язаного списку: $10^9$ передач (8× гірше)

На реальному обладнанні це переводиться на:
- Масив: мілісекунди
- Пов'язаний список: секунди

**Висновок:** Поведінка кешу **повністю домінує** алгоритмічну складність на сучасних системах.

### 2.3 Чому пов'язані списки все ще існують

Несвідомо поганої поведінки кешу, пов'язані списки зберігаються в:

1. **Функціональне програмування**
   - Незмінювальні операції списку через структурне спільне використання
   - Дружелюбні до copy-on-write
   - Амортизована O(n) загальний час для модифікацій

2. **Збір сміття**
   - Фаза маркування GC обходить живі об'єкти
   - Об'єкти вже розкидані в пам'яті (не можна поліпшити зі структурою даних)
   - Пов'язані списки захоплюють існуючий макет пам'яті

3. **Структури даних ядра**
   - Intrusive списки: вбудовані в структури для уникнення непрямого посилання
   - Використовуються в планувальниках, списках процесів

4. **Імовірнісні структури даних**
   - Skip-списки: шаровані випадкові пов'язані списки
   - Використовуються в Redis, LevelDB

## 📍 3. Стеки та черги: Абстрактні vs конкретні

### 3.1 Теоретичне визначення

**Стек (LIFO):** Абстрактний тип даних з операціями:
- push(x): додати елемент
- pop(): видалити та повернути найсвіжіший
- peek(): переглянути верхній елемент

**Черга (FIFO):** Абстрактний тип даних з операціями:
- enqueue(x): додати елемент
- dequeue(): видалити та повернути найстаріший
- peek(): переглянути передній елемент

Це **абстракції**, не реалізації. Обидва можуть бути реалізовані через:
- Динамічний масив
- Пов'язаний список
- Циркулярний буфер

### 3.2 Компроміси реалізації

**Стек на основі масиву:**
- push: O(1) амортизовано
- pop: O(1)
- Простір: O(n) з потенційною витратою

**Стек на основі пов'язаного списку:**
- push: O(1)
- pop: O(1)
- Простір: O(n) з накладними видатками на вузол

**Масив перемагає:** Краща локальність кешу, менше накладних видатків

**Пов'язаний список перемагає:** Ніколи не витрачає простір, жодного перевиділення

**Черга на основі масиву (наївна):**

Стан початку: `[_, _, _, _]`

Після операцій:
```
Enqueue 1: [1, _, _, _]
Enqueue 2: [1, 2, _, _]
Dequeue:   [_, 2, _, _]  ← Витрачена простір!
```

Проблема: Якщо тільки dequeue, передній вказівник витрачає простір.

**Рішення:** Циркулярна черга з вказівниками head та tail

**Вартість:** O(1) на операцію, без витрати, чиста реалізація

### 3.3 Deque (двостороння черга)

Підтримує O(1) операції на обох кінцях:
- pushFront, popFront, pushBack, popBack: O(1)

**Реалізація:** Циркулярний буфер з вказівниками head та tail

**Застосування:** Алгоритми ковзного вікна, оптимізація BFS

## 📍 4. Хеш-таблиці: Основи

### 4.1 Проблема колізії

Задано набір S ключів з універсуму U, зберігаємо їх для швидкого пошуку.

**Ідеальне хешування** (ідеал):
- Хеш-функція $h: U \to [0, m-1]$
- Жодних колізій якщо вибрати m = |S|
- O(1) гарантований пошук у гіршому випадку

**Проблема:** Універс U може бути величезним (наприклад, 64-бітні цілі числа). Побудова ідеального хешу для кожного набору даних дорога.

**Компроміс:** Використовуйте імовірнісні хеш-функції та обробляйте колізії.

### 4.2 Властивості хеш-функції

Хороша хеш-функція $h: U \to [0, m-1]$ повинна задовольняти:

**1. Детермінізм:** $h(x) = h(x)$ завжди
**2. Рівномірний розподіл:** Кожен бакет отримує $\approx \frac{|S|}{m}$ елементів
**3. Незалежність:** Значення хешу різних ключів незалежні
**4. Швидкість:** O(1) обчислення

На практиці, $h(x) = (ax + b) \mod m$ добре працює для цілих чисел (лінійна конгруентна).

Для рядків, накопичуйте хеш символів:
$$h(s) = \sum_{i=0}^{n} s[i] \cdot 31^i \mod m$$

### 4.3 Розв'язання колізій: Chaining vs Open Addressing

**Chaining:** Кожен бакет — це пов'язаний список елементів що конфліктують
- Пошук: $O(1 + \alpha)$ де $\alpha$ = коефіцієнт завантаження = $\frac{n}{m}$
- Вставка: $O(1 + \alpha)$
- Видалення: $O(1 + \alpha)$
- Простір: O(n + m)

Якщо ми підтримуємо $\alpha \leq 0.75$ через перевиділення, всі операції O(1) в середньому.

**Open addressing:** Усі елементи зберігаються в одному масиві, використовуйте зондування для пошуку порожніх слотів

Стратегії зондування:
- Лінійне: $h(x, i) = h(x) + i \mod m$ — страждає від групування
- Квадратичне: $h(x, i) = h(x) + c_1 i + c_2 i^2 \mod m$ — краще розповсюдження
- Подвійне хешування: $h(x, i) = h_1(x) + i \cdot h_2(x) \mod m$ — найкраще розповсюдження

Складність (α < 1):
$$\text{Очікуваний пошук} = \frac{1}{1 - \alpha}$$

Для α = 0.75: ~4 пошуки в середньому

### 4.4 Стратегія перевиділення

Коли коефіцієнт завантаження перевищує поріг (типово α > 0.75):

**Перевиділити:** Подвоїти розмір хеш-таблиці, перехешувати усі елементи
- Вартість: $O(n)$
- Частота: Кожні $\Theta(n)$ вставок
- Амортизована вартість: $O(1)$ на вставку

**Перевиділення робить O(1) середній випадок можливим.**

### 4.5 Аспект рандомізації

Пошук у хеш-таблиці O(1) **в середньому** над випадковими вхідними даними та випадковим вибором хеш-функції.

Гірший випадок: Антагоністичний вхід спричиняє всім елементам хешуватися в один бакет → O(n)

**Реальносвітова пом'якшення:**
- Використовуйте криптографічне хешування для недовірених вхідних даних (наприклад, мережеві пакети)
- SipHash: Швидке, безпечне, стійке до DoS атак
- Python 3+ використовує SipHash для запобігання DoS хеш-таблиці

## 📍 5. Дерева: Впорядковані структури

### 5.1 Бінарні дерева пошуку: Інформаційно-теоретичні межи

**Задача:** Підтримати впорядковану послідовність, підтримуйте:
- Пошук: Знайти елемент у O(log n)
- Вставка/Видалення: Підтримувати порядок у O(log n)
- Запити рангу: Знайти k-й найменший у O(log n)

**Нижня межа:** Будь-яка структура даних на основі порівнянь потребує $\Omega(\log n)$ порівнянь для пошуку.

**Доведення:** Дерево рішення має n листків (можливі результати пошуку). Глибина дерева = $\log_2 n$.

**BST досягає цього:** O(log n) якщо **збалансоване**

Незбалансоване BST дегенерує в пов'язаний список: O(n)

### 5.2 Самозбалансовуючі інваріанти

**AVL дерево:**
- Інваріант: Висоти лівого/правого підтерева відрізняються на ≤ 1
- Гарантія: Глибина ≤ 1.44 log(n)
- Операція: O(log n) з ротаціями

**Red-Black дерево:**
- Інваріант: Властивість чорної висоти
- Гарантія: Глибина ≤ 2 log(n+1)
- Операції: O(log n)

**B-дерево (для дискового I/O):**
- Інваріант: Усі листки на одній глибині, коефіцієнт розгалуження = розмір блоку
- Гарантія: $\log_B n$ дисків доступів (B-арний пошук)
- Використовується в: Базах даних, файлових системах

### 5.3 Heap: Семантика пріоритетної черги

**Властивість heap:** Батько ≤ дітям (min-heap)

**Структура:** Повне бінарне дерево (усі рівні заповнені окрім можливо останнього)

**Зберігається як:** Масив з неявними зв'язками:
- Ліва дитина i: 2i + 1
- Права дитина i: 2i + 2
- Батько i: ⌊(i-1)/2⌋

**Операції:**
- Вставка: O(log n) — бульбашка вгору
- Видалення мінімуму: O(log n) — бульбашка вниз
- Перегляд мінімуму: O(1)

**Не можна шукати:** Пошук довільного елементу потребує O(n)

**Реальне використання:** Алгоритм Дейкстри, планування завдань, пошук медіани

### 5.4 Trie: Структура специфічна для рядків

**Задача:** Підтримати швидкі запити префіксу на рядках

**Рішення:** Дерево де кожен вузол представляє позицію символу
- Вставити рядок "cat": ребра c→a→t, позначити t як термінальний
- Пошук "cat": O(довжина рядка), незалежно від розміру словника
- Пошук префіксу "ca": Знайти вузол у "a", перечислити все терміналів нижче

**Складність:**
- Вставка/Пошук: O(m) де m = довжина рядка
- Простір: O(розмір_алфавіту × унікальні_префікси)

**Компроміс:** Простір для швидких операцій префіксу

**Реальне використання:** Автозаповнення, маршрутизація IP, перевірка орфографії

## 📍 6. Графи: Структури зв'язків

### 6.1 Компроміси представлення

**Список суміжності:**
- Простір: O(V + E)
- Пошук сусіда: O(степінь)
- Ітерація ребер: O(E)
- Щільні графи: неефективні (E ≈ V²)

**Матриця суміжності:**
- Простір: O(V²)
- Пошук сусіда: O(1)
- Ітерація ребер: O(V²)
- Рідкі графи: витратні

**Виберіть список для рідких графів** (E << V²), **матрицю для щільних** (E ≈ V²)

### 6.2 Пошук у графі: Складність та властивості

**DFS (пошук у глибину):**
- Час: O(V + E)
- Простір: O(V) для стека рекурсії
- Застосування: Топологічне сортування, виявлення циклів

**BFS (пошук у ширину):**
- Час: O(V + E)
- Простір: O(V) для черги
- Застосування: Найкоротший шлях у невиражених, впорядкування рівнів

Обидва **оптимальні**: Жоден алгоритм не може розв'язати зв'язність без перевірки всіх вершин.

### 6.3 Найкоротші шляхи

**Алгоритм Дейкстри (невід'ємні ваги):**
- Використовуючи бінарну heap: O((V + E) log V)
- Використовуючи Fibonacci heap: O(E + V log V) — теоретично оптимально для однієї джерела

**Bellman-Ford (дозволені негативні ваги):**
- Час: O(V × E)
- Виявляє негативні цикли

**Floyd-Warshall (всі пари):**
- Час: O(V³)
- Простір: O(V²)

**Нижня межа:** Ω(E) — потрібно перевірити кожне ребро

Дейкстра досягає близько-оптимального з логарифмічним коефіцієнтом від heap.

### 6.4 Мінімальне кістякове дерево (MST)

**Задача:** З'єднати V вершин за допомогою V-1 ребер, мінімізуючи загальну вагу

**Нижня межа:** Ω(E log V) — інформаційно-теоретична (потрібна E порівняння, сортований порядок)

**Kruskal (Greedy за ребрами):**
- Сортування ребер: O(E log E)
- Union-Find: O(E α(V)) де α = обернений Акерман (≈ константа)
- Всього: O(E log E)

**Prim (Greedy від вершини):**
- Використовуючи бінарну heap: O((V + E) log V)
- Краще для щільних графів

## 📍 7. Union-Find: Диз'юнктивні множини

### 7.1 Задача та рішення

**Задача:** Розділити елементи на диз'юнктивні множини. Підтримувати:
- find(x): Яка множина містить x?
- union(x, y): Об'єднати множини що містять x та y

**Наївний підхід:**
- Кожний елемент зберігає ID множини
- find: O(1)
- union: O(n) — потрібно оновити всі ID

**Краще рішення:** Ліс диз'юнктивних множин з компресією шляху + union за рангом

### 7.2 Компресія шляху та Union за рангом

**Компресія шляху:** Коли пошукуємо корінь, зробити кожен вузол вказувати прямо на корінь
- Амортизована переваг: Робить пізніший пошук швидшим
- Ефект: Дерево стає дуже плоским

**Union за рангом:** Коли об'єднуємо, прикріпити менше дерево під більше
- Запобігає дегенерації в ланцюг
- Підтримує збалансовану структуру

**Складність з обома:** O(α(n)) на операцію, де α = обернений Акерман

Для всіх практичних n, α(n) ≤ 4. **Фактично константний час.**

### 7.3 Реальні застосування

- Kruskal's MST: O(E log E) сортування домінує, не union-find
- Виявлення циклів у графах
- Пов'язані компоненти
- Запити LCA (найменший спільний предок)
- Задачі еквівалентного класу

## 💡 Питання рівня Senior на співбесідах

1. **Чому масив амортизовано O(1) push, а не O(n)?**
   - Відповідь включає амортизований аналіз та амортизацію вартості перевиділення

2. **Розробіть структуру даних підтримуючу: Вставка, видалення, випадковий елемент у O(1) середньому.**
   - Відповідь: Хеш-таблиця + масив зі swap-remove трюком

3. **Як реалізувати LRU Cache з O(1) усіма операціями?**
   - Відповідь: Двосторонній пов'язаний список + хеш-таблиця (вказівники вузлів)

4. **Чому бази даних використовують B-дерева замість збалансованих BST?**
   - Відповідь: B-дерево мінімізує дискові I/O; відповідає розмір блоку до розгалуження

5. **Чи можна мати O(1) простір + O(1) доступ для довільних рідких масивів?**
   - Відповідь: Ні; теорема. Потрібно вибрати: O(n) простір АБО O(1) простір з O(log k) доступом

6. **Як SipHash запобігає DoS атакам на хеш-таблиці?**
   - Відповідь: Криптографічне хешування робить антагоністичні колізії обчислювально неможливими

7. **Яка теоретична нижня межа для порівняльного сортування?**
   - Відповідь: Ω(n log n); інформаційно-теоретична (n! переставок потребує log(n!) порівнянь)

## 🔑 Ключові висновки

1. **Амортизований аналіз** трансформує "поганий гіршій випадок" в "хороший середній" через розподіл вартості
2. **Ієрархія кешу** домінує реальною продуктивністю; просторова локальність перемагає алгоритмічні асимптоти
3. **Жодна ідеальна структура**—кожний вибір живе на поверхні компромісу
4. **Інформаційно-теоретичні межи** встановлюють абсолютні границі (наприклад, Ω(log n) для пошуку)
5. **Сучасні системи**—спеціалізація перемагає: B-дерева для дисків, trie для рядків, skip-списки для конкурентності
