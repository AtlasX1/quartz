# Семантичний HTML: Комплексний посібник для інженерів рівня L4

## Вступ

Семантичний HTML стосується використання розмітки HTML, яка передає значення про вміст, а не просто його представляє. Ця фундаментальна концепція визначає, як браузери, пошукові системи та допоміжні технології інтерпретують веб-документи. Цей посібник досліджує семантичний HTML на рівні інженерії, розглядаючи модель DOM, алгоритми структури документа, побудову дерева доступності та наслідки для SEO.

Розуміння семантичного HTML не є необов'язковим для старших інженерів—він утворює контракт між структурою документа, ефективністю рендерингу та відповідністю доступності.

## Частина 1: Структура документа та модель DOM

### 1.1 Фундаментальна архітектура DOM

Document Object Model (DOM) — це ієрархічна древовидна структура, що представляє зв'язок між HTML-елементами. Ця структура є фундаментальною для всіх наступних операцій браузера: рендерингу, макета, скриптування та доступності.

**Математичні основи:**

DOM — це кореневе упорядковане дерево з властивостями:
- $V$ = набір усіх вузлів (елементи, текстові вузли, коментарі)
- $E$ = зв'язки батько-дитина зі строгим упорядкуванням (зберігає порядок джерела)
- Для висоти документа $h$, максимальна складність глибини становить $O(h)$
- Повний обхід дерева становить $O(|V|)$ де $|V|$ — загальна кількість вузлів
- Операції запиту, як-от `querySelector`, виконують лінійний обхід DOM: $O(|V|)$ найгіршого випадку

**Оголошення типу документа:**

```html
<!DOCTYPE html>
```

DOCTYPE — це інструкція обробки, а не HTML-елемент. Вона оголошує версію документа й запускає критичну поведінку браузера:

| Режим | Спровокований | Модель коробки | Макет | Вплив на продуктивність |
|------|-------------|----------|--------|-------------------|
| Режим стандартів | HTML5 DOCTYPE присутній | CSS стандарт (border-box працює) | Сучасні алгоритми | Базовий |
| Режим сумісності | Відсутній/неправильний DOCTYPE | Спадщина (властивості коробки відрізняються) | Спадщина fallback | 15-30% повільніше |

**Наслідки режиму сумісності:**

Коли DOCTYPE відсутній:
- `box-sizing: border-box` не працює як очікується
- Вертикальне згортання маржи поводиться інакше
- Рендеринг `<table>` повертається до спадщинних алгоритмів
- Властивості кольору та шрифту наслідуються інакше
- Складність конвеєру рендерингу значно збільшується

**Найкраща практика:** Завжди включайте `<!DOCTYPE html>` на початку документа.

### 1.2 Основні елементи структури документа

HTML5 визначає логічну структуру з елементами контейнера, які встановлюють семантичне значення.

```html
<!DOCTYPE html>
<html lang="uk">
  <head>
    <!-- Метадані: назва, мета-теги, таблиці стилів, скрипти -->
    <meta charset="UTF-8">
    <title>Назва сторінки</title>
  </head>
  <body>
    <!-- Вміст: видимі елементи -->
  </body>
</html>
```

**Ключові атрибути:**

- Атрибут `lang` на `<html>`: Оголошує мову документа (критичне для читачів екрану, перевірки орфографії)
- Мета-тег `charset`: Оголошує кодування символів (запобігає помилкам кодування, проблемам безпеки)
- Мета-тег `viewport`: Керує мобільним рендерингом (передумова адаптивного дизайну)

```html
<meta charset="UTF-8">
<meta name="viewport" content="width=device-width, initial-scale=1.0">
<meta name="description" content="Опис сторінки для SEO">
```

**Примітка продуктивності:** Відсутнє або неправильне оголошення `charset` змушує браузер повторно аналізувати весь документ з правильним кодуванням, додаючи затримку 5-10мс при перезавантаженні.

## Частина 2: Елементи семантичного розділення

### 2.1 Елементи ознак та дерево доступності

Семантичні елементи встановлюють **області ознак**, які читачі екрану та браузери використовують для побудови дерева доступності. Це дерево — спрощене представлення DOM, оптимізоване для допоміжної технології.

**Таксономія елемента ознаки:**

| Елемент | Неявна ARIA роль | Дерево доступності | Сигнал SEO |
|---------|-------------------|-------------------|-----------|
| `<header>` | `banner` | Ознака верхнього рівня | Заголовок/введення сторінки |
| `<nav>` | `navigation` | Ознака навігації | Структура сайту |
| `<main>` | `main` | Ознака основного вмісту (один на документ) | Основна стаття/вміст |
| `<article>` | `article` | Одиниця вмісту | Автономна стаття |
| `<section>` | `region` (якщо названа) | Універсальна угрупація | Тематичний розділ |
| `<aside>` | `complementary` | Пов'язаний вміст | Бічна панель/додатковий |
| `<footer>` | `contentinfo` | Ознака колонтитула | Метадані документа |

**Приклад структури документа:**

```html
<body>
  <header>
    <nav>
      <!-- Меню навігації -->
    </nav>
  </header>
  
  <main>
    <article>
      <h1>Назва статті</h1>
      <section>
        <h2>Розділ 1</h2>
        <!-- Вміст -->
      </section>
      <section>
        <h2>Розділ 2</h2>
        <!-- Вміст -->
      </section>
    </article>
    
    <aside>
      <!-- Пов'язаний вміст -->
    </aside>
  </main>
  
  <footer>
    <!-- Метадані колонтитула -->
  </footer>
</body>
```

**Побудова дерева доступності:**

Коли браузер будує дерево доступності:
1. Він аналізує структуру DOM
2. Для кожного елемента розраховує:
   - **Назва**: З видимого тексту, `aria-label`, `aria-labelledby` або `title`
   - **Роль**: З семантичного елемента або явної ролі ARIA
   - **Стан**: Від disabled, checked, selected, тощо
   - **Властивості**: З атрибутів ARIA
3. Читачі екрану проходять це дерево, не DOM

**Вплив на продуктивність:** Семантична розмітка зменшує накладні витрати розрахунку дерева доступності. Неконсистема структура `<div>` змушує атрибути ARIA на кожному інтерактивному елементі, збільшуючи обробку атрибутів на 30-50%.

### 2.2 Елементи Article та Section

Елементи `<article>` та `<section>` часто плутаються. Їхня відмінність впливає на контур документа та семантичне значення.

**Елемент `<article>`:**

- Представляє **автономний, незалежно розповсюджуваний вміст**
- Приклади: блог-пост, новинна стаття, огляд продукту, коментар користувача
- Може бути вкладеним в інші елементи `<article>` (для вкладених коментарів, наприклад)
- Кожна `<article>` — це відмінна одиниця вмісту

```html
<article>
  <h1>Коментар користувача</h1>
  <p>Текст коментаря...</p>
  <time datetime="2024-12-16">16 грудня 2024</time>
</article>
```

**Елемент `<section>`:**

- Представляє **тематичну угрупацію пов'язаного вмісту**
- Приклади: Розділи в книзі, різні теми на сторінці, список функцій
- Повинен мати заголовок (`<h1>` через `<h6>`)
- Не є незалежно значимим

```html
<section id="introduction">
  <h2>Введення</h2>
  <p>Вміст розділу...</p>
</section>
```

**Порівняння:**

| Аспект | `<article>` | `<section>` |
|--------|-----------|-----------|
| Незалежність | Автономний | Тематична угрупація |
| Розповсюдження | Можна синдикувати незалежно | Частина більшого документа |
| Заголовок | Необов'язково (зазвичай присутній) | Повинен мати заголовок |
| Вкладення | Може вкладатися в `<article>` | Може вкладатися в `<section>` |
| Випадок використання | Автономні одиниці вмісту | Розподіл документа |

**Антипатерн:**

```html
<!-- ❌ НЕПРАВИЛЬНО: Використання <section> для стилізації/макета -->
<section class="container">
  <div class="wrapper">
    <!-- Вміст -->
  </div>
</section>

<!-- ✅ ПРАВИЛЬНО: Правильне семантичне вкладення з метою -->
<article>
  <h1>Назва статті</h1>
  <section>
    <h2>Перша тема</h2>
    <!-- Вміст -->
  </section>
</article>
```

## Частина 3: Текстові семантичні елементи

### 3.1 Акцент та сильна важливість

Текстові семантики вказують значення на рівні символу/фрази.

**`<strong>` vs `<b>`:**

- `<strong>`: Вказує на **сильну важливість** (семантичне значення); читач екрану підкреслює
- `<b>`: **Тільки жирне стилювання** (представлення); читач екрану читає нормально

```html
<!-- ✅ ПРАВИЛЬНО: Семантичне значення -->
<p>Це <strong>дуже важливо</strong> інформація.</p>

<!-- ❌ НЕПРАВИЛЬНО: Немає семантичного значення -->
<p>Це <b>дуже важливо</b> інформація.</p>
```

**`<em>` vs `<i>`:**

- `<em>`: Вказує на **акцент** (семантичний); змінює вимову в читачах екрану
- `<i>`: **Тільки курсив** (представлення); просто візуальне форматування

```html
<!-- ✅ ПРАВИЛЬНО: Семантичний акцент -->
<p>Мені <em>дійсно</em> сподобався цей фільм.</p>

<!-- ❌ НЕПРАВИЛЬНО: Немає семантичного значення -->
<p>Мені <i>дійсно</i> сподобався цей фільм.</p>
```

### 3.2 Спеціалізовані текстові елементи

| Елемент | Семантика | Випадок використання |
|---------|-----------|----------|
| `<code>` | Комп'ютерний код | Вбудовані фрагменти коду |
| `<pre>` | Попередньо відформатований текст | Блоки коду, ASCII-арт (зберігає пробіли) |
| `<kbd>` | Введення з клавіатури користувачем | "Натисніть `<kbd>Ctrl</kbd>+`<kbd>C</kbd>`" |
| `<samp>` | Вихід зразка | Вихід програми |
| `<var>` | Змінна | Математична/програмна змінна |
| `<abbr>` | Абревіатура | "The `<abbr title="World Wide Web">WWW</abbr>`" |
| `<cite>` | Джерело цитування | "Від `<cite>The Great Gatsby</cite>`" |
| `<q>` | Вбудоване цитування | "Він сказав `<q>Привіт</q>`" |
| `<blockquote>` | Блокове цитування | Багаторядкова цитата з атрибутом `cite` |
| `<time>` | Дата/час | `<time datetime="2024-12-16">16 грудня 2024</time>` |

**Приклад:**

```html
<p>
  Відповідно до <cite>ISO 8601</cite>, дата 
  <time datetime="2024-12-16">16 грудня 2024</time> 
  форматується як 2024-12-16.
</p>
```

## Частина 4: Форми та семантика введення

### 4.1 Структура форми та доступність

Форми — критичний семантичний компонент. Правильна структура є суттєвою для доступності та використання.

**Базова структура форми:**

```html
<form action="/submit" method="POST">
  <fieldset>
    <legend>Контактна інформація</legend>
    
    <label for="name">Ім'я:</label>
    <input type="text" id="name" name="name" required>
    
    <label for="email">Електронна пошта:</label>
    <input type="email" id="email" name="email" required>
    
    <label for="message">Повідомлення:</label>
    <textarea id="message" name="message" rows="5"></textarea>
    
    <button type="submit">Відправити</button>
  </fieldset>
</form>
```

**Критичні елементи:**

- **`<label>` з атрибутом `for`:** Пов'язує мітку із введенням через відповідання `id`
  - Створює більшу область клацання (мітка клацаєма)
  - Читачі екрану оголошують мітку, коли введення фокусується
  - Вимагається для відповідності доступності

- **`<fieldset>` і `<legend>`:** Групує пов'язані введення з пояснювальним текстом
  - Поліпшує організацію для складних форм
  - Читачі екрану оголошують `<legend>` при введенні набору полів

- **Атрибут введення `type`:** Визначає клавіатуру (мобільну), валідацію та рендеринг
  - `type="email"`: Валідує формат електронної пошти; показує клавіатуру електронної пошти на мобільному
  - `type="number"`: Показує числову клавіатуру; надає елементи керування счетчиком
  - `type="date"`: Показує збірник дати на підтримуваних браузерах
  - `type="tel"`: Показує телефонну клавіатуру

### 4.2 Datalist та пропозиції введення

```html
<label for="browser">Виберіть браузер:</label>
<input list="browsers" id="browser" name="browser">

<datalist id="browsers">
  <option value="Chrome">
  <option value="Firefox">
  <option value="Safari">
  <option value="Edge">
</datalist>
```

**Поведінка:**

- Користувач може або набирати, або вибирати зі списку
- Поліпшує UX над выпадаючим для довгих списків опцій
- Мобільні браузери можуть рендеритися як нативний вибір

## Частина 5: Контур документа та стратегія заголовків

### 5.1 Алгоритм контуру (W3C Specification)

Алгоритм контуру документа конструює ієрархічну структуру з елементів заголовків (`<h1>` через `<h6>`) та елементів розділення.

**Алгоритм (спрощений):**

```
1. Підтримувати стек відкритих розділів
2. При зустрічі заголовка <hN>:
   a. Якщо N < поточний рівень: закрити розділи до рівня N-1
   b. Якщо N == поточний рівень: створити рівноправний розділ
   c. Якщо N > поточний рівень: створити вкладені розділи для відсутніх рівнів
3. Результат: Ієрархічний контур, що відповідає структурі заголовків
```

**Приклад контуру:**

```html
<h1>Основна назва</h1>
  <!-- Рівень контуру 1 -->
  <h2>Розділ 1</h2>
    <!-- Рівень контуру 2 -->
    <h3>Розділ 1.1</h3>
      <!-- Рівень контуру 3 -->
    <h3>Розділ 1.2</h3>
  <h2>Розділ 2</h2>
    <h3>Розділ 2.1</h3>
```

**Виробляє контур:**

```
1. Основна назва
   1.1 Розділ 1
       1.1.1 Розділ 1.1
       1.1.2 Розділ 1.2
   1.2 Розділ 2
       1.2.1 Розділ 2.1
```

### 5.2 Антипатерни контуру

**Антипатерн 1: Пропуск рівнів заголовків**

```html
<!-- ❌ НЕПРАВИЛЬНО: Стрибає від h1 до h4 -->
<h1>Назва</h1>
<h4>Підрозділ</h4>
```

Вплив: Алгоритм контуру повинен створити неявні розділи `<h2>` і `<h3>`, збільшуючи складність обробки на $O(n)$ де $n$ = пропущені рівні.

**Антипатерн 2: Використання заголовків тільки для стилю**

```html
<!-- ❌ НЕПРАВИЛЬНО: Використовує h1 для стилю, а не семантики -->
<h1 style="font-size: 14px;">Звичайний текст</h1>
```

Вплив: Дерево доступності включає хибний заголовок, збиваючи з толку користувачів читачів екрану, які очікують структури навігації.

**Найкраща практика:**

```html
<!-- ✅ ПРАВИЛЬНО: Семантична ієрархія заголовків -->
<h1>Назва сторінки</h1>
<p>Вступний абзац</p>
<h2>Перший розділ</h2>
<p>Вміст розділу</p>
<h3>Підрозділ</h3>
<p>Вміст підрозділу</p>
```

## Частина 6: Мікродані та структуровані дані

### 6.1 Формат JSON-LD

Структуровані дані дозволяють машинам видобути семантичне значення з HTML. JSON-LD (JSON для пов'язаних даних) — рекомендований формат для SEO та реалізації розширеного фрагмента.

```html
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Article",
  "headline": "Як побудувати масштабовані веб-додатки",
  "author": {
    "@type": "Person",
    "name": "Джейн Архітектор"
  },
  "datePublished": "2024-12-16",
  "dateModified": "2024-12-16",
  "image": "https://example.com/image.jpg",
  "articleBody": "Вміст статті...",
  "mainEntity": {
    "@type": "Thing",
    "name": "Архітектура веб-додатків"
  }
}
</script>
```

### 6.2 Типи Schema.org

Поширені типи схеми для веб-вмісту:

| Тип | Властивості | Випадок використання |
|-----|-----------|----------|
| `Article` | headline, author, datePublished, articleBody | Блог-пости, новини |
| `NewsArticle` | Розширює Article | Новинний вміст (вища вага при пошуку) |
| `BlogPosting` | Розширює Article | Записи в блозі |
| `Product` | name, price, offers, review | Електронна комерція |
| `Organization` | name, url, logo, address | Інформація про бізнес |
| `Person` | name, email, sameAs | Інформація про автора/контакт |
| `Event` | name, startDate, endDate, location | Список подій |
| `LocalBusiness` | name, address, telephone, email | Місцевий бізнес |

### 6.3 Вплив на SEO

**Включення розширеного фрагмента:**

Структуровані дані дозволяють Google відображати поліпшені результати пошуку (розширені фрагменти):
- Розширені фрагменти статей: Поліпшення CTR на 20-30%
- Розширені фрагменти продуктів: Показана ціна, наявність, відгуки
- Розширені фрагменти подій: Дата, місцезнаходження, наявність квитків

**Розрахунок:**

Для результату пошуку, що показує розширений фрагмент vs. стандартне перелічення:
- Стандартний CTR: базовий
- Розширений CTR: базовий × 1.2 до 1.3

Приклад: 1000 показів → 30 стандартних кліків → 36-39 кліків з розширеним фрагментом

**Накладні витрати обробки:** Аналізатор JSON-LD Google додає складність $O(n)$ де $n$ = розмір JSON. Затримка аналізу для складних документів може досягати 500мс.

## Частина 7: Прогресивне покращення та граціозна деградація

### 7.1 Стратегія прогресивного покращення

Прогресивне покращення будує веб-додатки багатошаровим підходом:

1. **Шар 1 (Фундамент):** Самий семантичний HTML (базова функціональність)
2. **Шар 2 (Покращення):** CSS (представлення та макет)
3. **Шар 3 (Розширений):** JavaScript (інтерактивність та динамічна поведінка)

```html
<!-- Шар 1: Семантика HTML працює без CSS чи JS -->
<form action="/search" method="GET">
  <input type="search" name="q" placeholder="Пошук...">
  <button type="submit">Пошук</button>
</form>

<!-- Шар 2: CSS покращує представлення -->
<style>
  form { display: flex; gap: 1rem; }
  input { flex: 1; padding: 0.5rem; }
</style>

<!-- Шар 3: JavaScript покращує AJAX, дебаунсингом, тощо -->
<script>
  form.addEventListener('input', () => {
    // Отримати пропозиції через AJAX
  });
</script>
```

**Обробка збоїв:**

- Якщо CSS не вдається завантажити: Форма залишається функціональною (семантичний HTML)
- Якщо JavaScript не вдається: Форма все ще надсилає через сервер (немає AJAX)
- Якщо обидва не вдаються: Форма працює на базовому рівні

### 7.2 Граціозна деградація на практиці

```html
<!-- Fallback для елемента відео -->
<video controls width="320" height="240">
  <source src="movie.mp4" type="video/mp4">
  <source src="movie.webm" type="video/webm">
  <p>Ваш браузер не підтримує відео HTML5. 
     <a href="movie.mp4">Завантажити файл</a>.</p>
</video>
```

Поведінка браузером:
- Браузери з підтримкою HTML5: Грати відео з елементами керування
- Старіші браузери: Показати повідомлення fallback з посиланням на завантаження
- Усі користувачі отримують доступ до вмісту

## Частина 8: Поширені помилки семантичного HTML

### Помилка 1: Використання `<div>` для всього

```html
<!-- ❌ НЕПРАВИЛЬНО -->
<div class="header">
  <div class="nav">
    <a href="/">Головна</a>
  </div>
</div>

<!-- ✅ ПРАВИЛЬНО -->
<header>
  <nav>
    <a href="/">Головна</a>
  </nav>
</header>
```

Вплив: Користувачі читачів екрану втрачають структуру навігації; SE-краулери борються з розумінням макета.

### Помилка 2: Використання теґів заголовків для стилізації

```html
<!-- ❌ НЕПРАВИЛЬНО: Заголовок використовується тільки для візуального ефекту -->
<h1 style="font-size: 12px; color: gray;">Назва бічної панелі</h1>

<!-- ✅ ПРАВИЛЬНО: Правильна семантична ієрархія -->
<h2>Назва бічної панелі</h2>
```

### Помилка 3: ARIA зловживання

```html
<!-- ❌ НЕПРАВИЛЬНО: ARIA на нативному елементі з міткою -->
<button aria-label="Закрити">✕</button>

<!-- ✅ ПРАВИЛЬНО: Нативна семантика вже надає доступність -->
<button>✕</button>

<!-- ✅ ТАКОЖ ПРАВИЛЬНО: Використовуйте title, якщо потрібен додатковий контекст -->
<button title="Закрити діалог">✕</button>
```

### Помилка 4: Відсутній альтернативний текст

```html
<!-- ❌ НЕПРАВИЛЬНО: Зображення без альтернативного тексту -->
<img src="chart.jpg">

<!-- ✅ ПРАВИЛЬНО: Описовий альтернативний текст -->
<img src="chart.jpg" alt="Продажі по кварталам: Q1 $50M, Q2 $62M, Q3 $71M, Q4 $85M">

<!-- ✅ ПРАВИЛЬНО: Декоративне зображення позначено як таке -->
<img src="decorative-line.svg" alt="">
```

## Частина 9: Питання для інтерв'ю

### Концептуальні питання

**Q1: Поясніть різницю між `<article>` і `<section>`. Коли б ви використовували кожен з них?**

**Структура відповіді:**
- `<article>`: Автономний, незалежно розповсюджуваний вміст (блог-пост, коментар, огляд продукту)
- `<section>`: Тематична угрупація пов'язаного вмісту (розділ, розділ теми)
- `<article>` може містити кілька елементів `<section>`
- Використовуйте `<section>` для структурної організації; використовуйте `<article>` для одиниць вмісту

**Q2: Що таке алгоритм контуру документа і чому правильна ієрархія заголовків важлива?**

**Структура відповіді:**
- Алгоритм конструює ієрархічну структуру з теґів `<h1>` через `<h6>`
- Читачі екрану використовують контур для навігації
- Неправильна ієрархія (пропуск рівнів) змушує перерахування контуру ($O(n)$ вартість)
- Пошукові системи використовують структуру заголовків для розуміння важливості вмісту

**Q3: Коли слід використовувати семантичний HTML vs. ARIA, і що є принципом цього?**

**Структура відповіді:**
- Перше правило ARIA: Використовуйте нативний HTML, якщо він існує
- ARIA — це останній засіб для користувацьких віджетів
- Читачі екрану працюють краще з семантичним HTML
- ARIA додає тягар обслуговування; семантичний HTML само-документується

### Практичні сценарії

**Q4: Ви будуєте багатостатейний блог-фід, де кожна стаття має коментарі. Як би ви структурували HTML семантично?**

**Структура відповіді:**
```html
<main>
  <article>
    <h1>Назва статті</h1>
    <!-- Вміст статті -->
    
    <section id="comments">
      <h2>Коментарі</h2>
      <article>
        <h3>Коментар від User1</h3>
        <!-- Вміст коментаря -->
      </article>
      <article>
        <h3>Коментар від User2</h3>
        <!-- Вміст коментаря -->
      </article>
    </section>
  </article>
</main>
```

**Q5: Сторінка має бічну панель з "пов'язаними статтями" та основної статтею. Як би ви структурували це як семантично правильне?**

**Структура відповіді:**
```html
<main>
  <article>
    <!-- Вміст основної статті -->
  </article>
</main>
<aside>
  <h2>Пов'язані статті</h2>
  <!-- Посилання на пов'язаний вміст -->
</aside>
```

## Ключові висновки

1. **Семантичний HTML є фундаментальним** - Він встановлює контракт між структурою документа та інтерпретацією браузером/допоміжною технологією
2. **Контур документа має значення** - Правильна ієрархія заголовків допомагає читачам екрану та пошуковим системам розумити важливість вмісту
3. **Прогресивне покращення працює** - Будуйте шари: семантичний HTML спочатку, потім CSS, потім JavaScript
4. **ARIA — це fallback** - Використовуйте семантичні HTML-елементи, коли це можливо; ARIA — для користувацьких віджетів
5. **Структуровані дані поліпшують виявлення** - JSON-LD дозволяє розширені фрагменти, поліпшуючи CTR на 20-30%
6. **Семантика форм критична** - Правильні атрибути `<label>`, `<fieldset>`, введення `type` забезпечують доступність та використання
7. **Алгоритм контуру документа має наслідки складності** - Пропуск рівнів заголовків додає накладні витрати $O(n)$
8. **Дерево доступності залежить від семантики** - Читачі екрану будують дерева з семантичної розмітки; неконсистема HTML вимагає ARIA

## Висновок

Семантичний HTML — це не про дотримання правил W3C для відповідності—це про створення документів, які:
- Зрозумілі машинам (браузери, пошукові системи, читачі екрану)
- Залишаються функціональними, коли CSS та JavaScript не спрацьовують
- Масштабуються до складних вкладених структур без ARIA-хаків
- Одночасно поліпшують SEO та досвід користувача

Старші інженери визнають, що семантичні вибори, зроблені на рівні HTML, каскадуються через всю систему: ефективність рендерингу, реалізація доступності, ефективність SEO та утримання коду — все залежить від правильної семантичної структури.

Дисципліна семантичного HTML розрізняє інженерію від кодування: різниця між веб-сайтом, що працює, і веб-сайтом, що тривалий.
