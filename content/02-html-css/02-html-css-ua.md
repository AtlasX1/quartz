# HTML & CSS: Комплексний посібник для інженерів рівня L4

## Вступ

HTML (HyperText Markup Language) та CSS (Cascading Style Sheets) утворюють фундаментальний шар веб-розробки. Цей посібник досліджує ці технології на рівні інженерії, переходячи за межі вступних туторіалів для вивчення архітектурних принципів, впливу на продуктивність, вимог до доступності та виробничих патернів.

Цей документ структурований для старших інженерів, архітекторів та осіб, які готуються до складних технічних інтерв'ю. Кожен розділ поєднує теоретичні основи з практичними виробничими розглядами, висвітлюючи математичні та алгоритмічні аспекти, які часто ігнорують у традиційних матеріалах навчання.

## Частина 1: Архітектура семантичного HTML

### 1.1 Структура документа та модель DOM

HTML-документи встановлюють ієрархічну древовидну структуру — Document Object Model (DOM) — яка утворює контракт між необробленою розміткою та механізмами рендерингу браузера. Ця структура не є просто синтаксичною; вона кодує семантичну інформацію, що впливає на доступність, SEO та ефективність рендерингу.

**Математичні основи:**

Дерево DOM є кореневим упорядкованим деревом, де:
- $V$ = набір усіх вузлів (елементи, текстові вузли, коментарі)
- $E$ = зв'язки батько-дитина зі строгим упорядкуванням
- Для висоти документа $h$, складність обходу становить $O(|V|)$
- Операції запиту, як-от `querySelector`, працюють у $O(|V|)$ у найгіршому випадку через лінійний обхід DOM

**Тип документа та оголошення:**

```html
<!DOCTYPE html>
```

DOCTYPE — не HTML-елемент, а інструкція обробки, що оголошує версію документа. У HTML5 він запускає **режим стандартів** у всіх сучасних браузерах. Його відсутність запускає **режим сумісності**, де:
- Розрахунки коробки моделі відрізняються (немає семантики `box-sizing: border-box`)
- Вертикальне згортання маржі поводиться інакше
- Рендеринг `<table>` переключається на алгоритми спадщини
- Продуктивність знижується на 15-30% у конвеєрі рендерингу

**Елементи контейнера семантики:**

| Елемент | Семантика | Вплив на дерево доступності | Вплив SEO |
|---------|-----------|------------------------------|-----------|
| `<header>` | Вступний вміст або контейнер навігації | Область ознаки (неявна `role="banner"`) | Сигналізує заголовки розділу сторінки |
| `<nav>` | Основні посилання навігації | Область ознаки (неявна `role="navigation"`) | Вказує на структуру сайту |
| `<main>` | Основний вміст сторінки | Область ознаки; тільки одна дозволена на документ | Якір основного вмісту для SE-краулерів |
| `<article>` | Автономний вміст | Неявна `role="article"`; впливає на контур документа | Сигналізує незалежні одиниці вмісту |
| `<section>` | Тематична угрупація | Неявна `role="region"` якщо названа | Універсальна семантична угрупація |
| `<aside>` | Пов'язаний, але дотичний вміст | Область ознаки; неявна `role="complementary"` | Сигнал бічної панелі/додаткового вмісту |
| `<footer>` | Інформація колонтитула документа | Неявна `role="contentinfo"` | Сигнал метаданих колонтитула |

**Критичне розуміння:** Семантичний HTML — не просто естетична перевага — він безпосередньо впливає на:
1. **Побудову дерева доступності:** Читачі екрану аналізують семантичні теги для побудови структур навігації
2. **Оптимізація рендерингу:** Браузери оптимізують області ознак по-різному
3. **Краулінг SEO:** Боти пошукових систем призначають вагу релевантності на основі семантичного вкладення
4. **Ефективність мобільних пристроїв:** Семантичні регіони дозволяють браузерам мобільних пристроїв застосовувати оптимізацію рендерингу для конкретного вмісту

### 1.2 Контур документа та стратегія заголовків

Контур документа — це формальна структура, отримана з ієрархії заголовків ($h1$ до $h6$) та елементів розділів. Цей контур визначає, як допоміжні технології представляють структуру сторінки.

**Алгоритм контуру (W3C):**

Алгоритм підтримує **стек розділів** та **покажчик поточного розділу**:
1. При зустрічі з `<hN>` де $N < $ поточний рівень: закрити розділи до висоти стека дорівнює $N-1$
2. При зустрічі з `<hN>` де $N = $ поточний рівень: створити рівноправний розділ
3. При зустрічі з `<hN>` де $N > $ поточний рівень: створити вкладені розділи для кожного відсутнього рівня

**Приклад контуру:**

```html
<h1>Основна назва</h1>           <!-- Рівень контуру 1 -->
  <h2>Розділ А</h2>          <!-- Рівень контуру 2 -->
    <h3>Підрозділ А1</h3>    <!-- Рівень контуру 3 -->
    <h3>Підрозділ А2</h3>    <!-- Рівень контуру 3 -->
  <h2>Розділ В</h2>          <!-- Повернення до рівня 2 -->
```

**Вплив на продуктивність:** Алгоритм контуру працює $O(h)$ де $h$ — глибина заголовків. Глибоко вкладена неправильна структура заголовків (напр., стрибок від `h1` до `h4`) змушує повторний розрахунок контуру, додаючи $O(n)$ операцій де $n$ — мають на увазі розділи.

### 1.3 Ролі, стани та властивості ARIA

ARIA (Accessible Rich Internet Applications) розширює HTML-семантику, коли вбудовані елементи недостатні. Однак принцип полягає у **відсутності ARIA краще за погану ARIA**.

**Правила впровадження ARIA:**

1. **Перше правило ARIA:** Якщо існує вбудований HTML-елемент із необхідною семантикою, використовуйте його замість ARIA
2. **Друге правило:** Не використовуйте ARIA для виправлення поганої семантичної структури—виправте HTML
3. **Третє правило:** Завжди зберігайте видимі, програмуючи визначені імена для елементів, розширених ARIA

**Таксономія ролей:**

```
Ролі
├── Абстрактні ролі (базові класи; ніколи не використовуйте прямо)
│   ├── command (подібні до кнопки спусками дій)
│   ├── composite (дерево, меню, табліст)
│   ├── input (подібні до форми віджети)
│   ├── landmark (області навігації)
│   └── structure (неінтерактивна семантична угрупація)
├── Ролі ознак (неявні через семантичні елементи)
│   ├── banner, contentinfo, main, navigation, complementary, search, region
├── Абстрактні ролі віджетів
├── Ролі структури документа
└── Ролі живих регіонів
```

**Критичні властивості:**

- `aria-label`: Видима назва переозначення для елемента. Використовуйте розумно; вважайте за краще `<label>` або видимий текст
- `aria-labelledby`: Посилання на елемент, що надає назву; підтримує розрахунок імені читача екрану
- `aria-describedby`: Розширений опис окремо від основної назви
- `aria-live`: Позначає регіон для оновлень реального часу; значення — `polite` (нижча пріоритет), `assertive` (перебити), `rude` (оновлення поза екраном)
- `aria-hidden="true"`: Видаляє з дерева доступності; використовуйте для декоративного/надлишкового вмісту

**Антипатерн:**

```html
<!-- ❌ НЕПРАВИЛЬНО: Декоративна роль без семантичного HTML -->
<div role="button" aria-label="Закрити">✕</div>

<!-- ✅ ПРАВИЛЬНО: Використовуйте вбудований елемент -->
<button aria-label="Закрити">✕</button>

<!-- ❌ НЕПРАВИЛЬНО: Aria-label на елементі з видимим текстом -->
<span aria-label="Важливо">⚠️</span>

<!-- ✅ ПРАВИЛЬНО: Використовуйте атрибут title або видимий текст -->
<span title="Важливо">⚠️</span>
```

### 1.4 Мікродані та структуровані дані

Структуровані дані дозволяють машинам видобути значення з HTML-вмісту. Пошукові системи, соціальні мережі та процесори розширених фрагментів залежать від стандартизованих форматів мікроданих.

**Формати:**

1. **Мікродані (вбудовані HTML5):** Атрибути (`itemscope`, `itemtype`, `itemprop`) вбудовані в розмітку
2. **RDFa:** Розмітка семантики на основі графіка (спадаючого використання)
3. **JSON-LD:** Кодування JSON зв'язаних даних у тегах `<script type="application/ld+json">` (рекомендується для SEO)

**Приклад (JSON-LD для статті):**

```html
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Article",
  "headline": "Як побудувати архітектуру мікросервісів",
  "author": {
    "@type": "Person",
    "name": "Джейн Архітектор"
  },
  "datePublished": "2024-12-16",
  "image": "https://example.com/article-image.jpg",
  "mainEntity": {
    "@type": "Thing",
    "name": "Мікросервіси"
  }
}
</script>
```

**Вплив на SEO-продуктивність:**

Розширені фрагменти (структуровані результати даних) показують **поліпшення CTR на 20-30%** у результатах пошуку Google. Включення типу schema.org поліпшує оцінку релевантності, особливо для:
- Домени статей/новин: властивості `datePublished`, `author`
- Електронна комерція: `Product`, `offers`, агрегація `review`
- Місцеві: `Organization`, `Address`, `GeoCoordinates`

**Складність впровадження браузером:** Аналіз JSON-LD додає $O(n)$ операцій де $n$ — розмір JSON. Google Search Console обробляє JSON-LD асинхронно; затримка аналізу може досягати 500мс для складних документів.

## Частина 2: Основи CSS та конвеєр рендерингу

### 2.1 Каскад, специфічність та модель наслідування

CSS працює на трирівневому каскаді, специфічність визначає пріоритет у межах кожного шару.

**Шари каскаду (CSS Cascade Spec L4):**

```
Порядок важливості (найвищий до найнижчого):
1. Переходи анімацій (джерело користувача-агента)
2. !important декларації (джерело автора)
3. Застосування анімацій
4. Декларації походження автора
5. Декларації користувача
6. Декларації користувача-агента
```

**Розрахунок специфічності:**

Специфічність — це 4-кортеж $(a, b, c, d)$ де:
- $a$ = 1 якщо вбудований `style=""`, інакше 0
- $b$ = кількість селекторів ID
- $c$ = кількість селекторів класу, атрибута та псевдокласу
- $d$ = кількість селекторів елемента та псевдоелемента

Порівняння: $(1, 0, 0, 0) > (0, 100, 100, 100)$ (вбудована завжди побеждає)

**Приклади:**

| Селектор | Специфічність | Розрахунок |
|----------|-------------|-----------|
| `*` | $(0,0,0,0)$ | Універсальний |
| `button` | $(0,0,0,1)$ | 1 елемент |
| `button.primary` | $(0,0,1,1)$ | 1 клас + 1 елемент |
| `#header button.primary` | $(0,1,1,1)$ | 1 ID + 1 клас + 1 елемент |
| `style="color:red"` | $(1,0,0,0)$ | Вбудований стиль |

**Модель наслідування:**

Властивості, які наслідуються (за замовчуванням): `color`, `font-*`, `line-height`, `letter-spacing`, `word-spacing`, `visibility`, `cursor`, `list-style-*`.

Не наслідуються: `margin`, `padding`, `border`, `width`, `height`, `background`, `position`.

**Розгляд ефективності:** Браузер повинен обчислити значення наслідування для кожної успадкованої властивості на кожному елементі. Для документа з $n$ елементами та $m$ успадкованими властивостями, ця операція становить $O(n \cdot m)$ у кожному циклі переобчислення CSS.

### 2.2 Дисплей та потіковий макет

Властивість `display` визначає, як елемент бере участь у макеті—його **зовнішній дисплей** (як він підходить в батьківський) та **внутрішній дисплей** (як він розташовує дітей).

**Значення дисплею та потік:**

| Значення | Зовнішній | Внутрішній | Значущість |
|---------|---------|---------|---|
| `block` | Блокова коробка рівня | Блок FFC | Повна ширина за замовчуванням; вертикальне згортання маржи |
| `inline` | Вбудована коробка рівня | Вбудований FFC | Ширина ігнорується; маржа/доповнення асиметричне |
| `inline-block` | Вбудована коробка рівня | Блок FFC | Вбудоване позиціонування; поважає ширину/висоту |
| `flex` | Контейнер flex | Flex FFC | Одновимірний макет з контролем вирівнювання |
| `grid` | Контейнер сітки | Сітка FFC | Двовимірний макет з явним позиціонуванням |
| `table` | Коробка обгортки таблиці | Таблиця FFC | Спадщина табульованого макету моделі |

**Контекст форматування:**

Контекст форматування — це незалежне середовище макета. Ключові типи:

1. **Блок форматування контексту (BFC):** Вертикальне укладання; згортання маржи відбувається
2. **Контекст форматування вбудованого (IFC):** Горизонтальні вбудовані коробки; коробки ліній встановлюють базові лінії
3. **Контекст форматування flex (FFC):** Елементи flex вирівнюються на головних/перехресних осях
4. **Контекст форматування сітки (GFC):** Елементи сітки займають явні комірки

**Умови спускання BFC:**

BFC створюється при:
- Елемент є корінь (`<html>`)
- `display: block` з `overflow` != `visible`
- `display: flow-root` (явне створення BFC)
- `position: absolute` або `fixed`
- Контейнер flex/сітка

**Вплив на продуктивність:** Кожен BFC запускає незалежний розрахунок макета. Для $n$ незалежних BFC, час макета становить $\Sigma O(BFC_i)$ замість $O(n)$ глобального макета. Надмірне створення BFC (напр., `overflow: hidden` для очищення) фрагментизує макет, збільшуючи цикли перерахування.

### 2.3 Моделі позиціонування

Позиціонування CSS визначає, як елементи розташовуються відносно їхнього блока утримання.

**Позиціонування значень:**

| Значення | Блок утримання | Застосованість компенсації | Z-стекування |
|---------|---------------------|----------------------|-----------|
| `static` (за замовчуванням) | Нормальний потік | Ігнорується | Ні |
| `relative` | Нормальна позиція | Відносно нормальної позиції | Створює SC* |
| `absolute` | Позиціонований предок | Відносно блока утримання | Створює SC |
| `fixed` | Видимовікно | Відносно видимовікна | Створює SC |
| `sticky` | Скролер | Відносно видимовікна у зоні прокрутки | Створює SC |

*SC = контекст стекування

**Контекст стекування та Z-index:**

Контекст стекування — це 3D модель шарування де елементи упорядковуються по:
1. Корінь контексту стекування
2. Елементи з `z-index < 0`
3. Нащадки рівня блока у нормальному потоці
4. Нащадки float
5. Нащадки вбудовані/вбудовані-блока у нормальному потоці
6. Елементи з `z-index: auto` або `0`
7. Елементи з `z-index > 0`

**Критичне правило:** `z-index` порівнює тільки рівноправні контексти стекування. Елемент з `z-index: 9999` у контексті стекування з нижчим порядком кореня не може перевершити елемент з `z-index: 1` у вищому контексті стекування.

**Неявне створення контексту стекування:**

Сучасний CSS створює контексти стекування для:
- `opacity < 1`
- `transform` (будь-яке значення крім `none`)
- `mix-blend-mode` != `normal`
- `filter` (будь-яке значення крім `none`)
- `backdrop-filter` (будь-яке значення крім `none`)
- `will-change` властивості
- Контейнери flex/сітки з деякими властивостями

Це створює сюрпризи в шаруванні, коли `opacity` застосовується для візуальних ефектів, але ненавмисне створює контекст стекування.

### 2.4 Згортання маржи та коробка моделі

Модель коробки CSS описує розподіл простору навколо вмісту.

**Шари коробки моделі (зовні до середини):**

```
┌─────────────────────────────┐
│        Маржа                │
│  ┌───────────────────────┐  │
│  │      Межа             │  │
│  │  ┌───────────────────┐│  │
│  │  │   Доповнення      ││  │
│  │  │  ┌───────────────┐││  │
│  │  │  │  Вміст        │││  │
│  │  │  └───────────────┘││  │
│  │  └───────────────────┘│  │
│  └───────────────────────┘  │
└─────────────────────────────┘
```

**Правила згортання маржи:**

Вертикальні маржі між елементами на рівні блока згортаються до максимальної маржи:
- Між прилеглими рівноправниками: $max(M_{top}, M_{bottom})$
- Батько-дитина (якщо межа/доповнення не розділяє): маржи згортаються вертикально
- Маржи ніколи не згортаються горизонтально

Приклад:
```css
/* Прилеглі рівноправники */
.box-a { margin-bottom: 20px; }
.box-b { margin-top: 30px; }
/* Згорнута відстань: max(20px, 30px) = 30px */

/* Без згортання: межа BFC */
.box-c { overflow: hidden; }
.box-c + .box-d /* Маржи не згортаються */
```

**Властивість Box-sizing:**

- `content-box` (за замовчуванням): `width` = тільки ширина вмісту; межа/доповнення додано зовні
- `border-box`: `width` включає межу + доповнення; ширина вмісту = $w - padding - border$

**Примітка продуктивності:** `box-sizing: border-box` усуває складні розрахунки ширини у макеті, зменшуючи складність перерахування. Сучасна найкраща практика — `* { box-sizing: border-box }` на корені таблиці стилів.

## Частина 3: Передові техніки макета CSS

### 3.1 Flexbox (Макет гнучкої коробки)

Flexbox — це одновимірна модель макета, оптимізована для розподілу простору вздовж однієї осі (головної або перехресної).

**Властивості контейнера:**

| Властивість | Значення | Ефект |
|----------|--------|--------|
| `flex-direction` | `row`, `column`, `row-reverse`, `column-reverse` | Орієнтація головної осі |
| `flex-wrap` | `nowrap`, `wrap`, `wrap-reverse` | Поведінка розбиття строки |
| `justify-content` | `flex-start`, `center`, `space-between`, `space-around`, `space-evenly` | Вирівнювання головної осі |
| `align-items` | `stretch`, `flex-start`, `center`, `baseline`, `flex-end` | Вирівнювання перехресної осі (один рядок) |
| `align-content` | Те ж, що `justify-content` | Вирівнювання перехресної осі (кілька рядків) |
| `gap` | Довжина або `calc()` | Простір між елементами |

**Властивості елемента:**

- `flex-basis`: Розмір за замовчуванням до розподілу вільного простору ($0 ≤ flex-basis$)
- `flex-grow`: Коефіцієнт зростання; розподіляє позитивний вільний простір пропорційно ($\text{growth}_i = \frac{\text{grow}_i}{\sum \text{grow}_j}$)
- `flex-shrink`: Коефіцієнт скорочення; розподіляє негативний вільний простір пропорційно
- `flex`: Скорочення для `flex-grow`, `flex-shrink`, `flex-basis`
- `align-self`: Переозначення `align-items` контейнера для окремого елемента
- `order`: Візуальне переупорядкування (не впливає на порядок DOM; вплив на читача екрану)

**Математична модель:**

Дана ширина контейнера $W$, елементи з базисом $b_i$ та шириною вмісту $c_i$:

1. **Розрахунок початкового простору:** $S = W - \sum b_i$
2. **Якщо $S > 0$ (позитивний вільний простір):** $\text{adjusted}_i = b_i + S \cdot \frac{g_i}{\sum g_j}$
3. **Якщо $S < 0$ (негативний вільний простір):** $\text{adjusted}_i = b_i + S \cdot \frac{s_i}{\sum s_j}$

**Характеристики продуктивності:**

Макет Flexbox працює в $O(n \log n)$ для сортування елементів, якщо `flex-wrap: wrap` увімкнено (розбиття ліній вимагає двох проходів). Однолінійний flex становить $O(n)$.

**Поширені патерни:**

1. **Центрування:** `display: flex; justify-content: center; align-items: center`
2. **Простір між стовпцями:** `justify-content: space-between` з `flex-basis: auto`
3. **Елементи рівної ширини:** `flex: 1` на всіх елементах
4. **Макет бічної панелі:** Ліва бічна панель `flex: 0 0 200px`; вміст `flex: 1`

### 3.2 CSS Grid

CSS Grid — це двовимірна система макета з явними дорожками рядів та стовпців.

**Властивості контейнера:**

| Властивість | Приклад | Ефект |
|----------|---------|--------|
| `grid-template-columns` | `200px 1fr 200px` | Явні дорожки стовпців |
| `grid-template-rows` | `auto 1fr auto` | Явні дорожки рядів |
| `grid-auto-columns` / `grid-auto-rows` | `minmax(100px, 1fr)` | Неявна розмірність дорожки |
| `gap` | `20px 10px` | Водовідвідні рядів і стовпців |
| `grid-template-areas` | Назване області для розміщення | Макет шаблону |
| `justify-items` / `align-items` | `center`, `start`, `end` | Вирівнювання дитини за замовчуванням |

**Ключові одиниці:**

- `fr` (дріб): Розподіляє вільний простір; $n$ одиниці fr ділять простір на $n$ рівних частин
- `minmax(min, max)`: Дорожка розтягується між межами
- `auto`: Розмір на основі вмісту (ширина найширшої дитини)
- `repeat(count, pattern)`: Повторення; `repeat(auto-fit, minmax(200px, 1fr))` створює адаптивні стовпці

**Розміщення елемента сітки:**

Елементи можуть бути розміщені:
1. **Неявно:** Вміст тече у порядку читання
2. **Явно:** `grid-column: 1 / 3` (лінії 1-3), `grid-row: 1 / span 2` (2 рядки)
3. **За назвою:** `grid-area: header` з `grid-template-areas: "header header"`

**Модель продуктивності:**

Макет сітки має $O(n + m)$ складність де $n$ = стовпці, $m$ = рядки. Явне розміщення (названі області) швидше за неявне розміщення авто, яке вимагає елемент-за-елементом аналіз.

**Адаптивний рисунок сітки:**

```css
.grid {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(250px, 1fr));
  gap: 20px;
}

/* Запитики щодо медіа не потрібні; сітка реагує автоматично */
```

### 3.3 Адаптивний дизайн та запити контейнера

**Запити медіа на основі видимовікна:**

Запити медіа застосовують стилі умовно на основі характеристик видимовікна.

```css
@media (min-width: 768px) {
  /* Планшет та більше */
}

@media (orientation: landscape) {
  /* Альбомна орієнтація */
}

@media (prefers-color-scheme: dark) {
  /* Користувач переважає темний режим у налаштуваннях ОС */
}

@media (prefers-reduced-motion: reduce) {
  /* Доступність: користувач переважає мінімальну анімацію */
}
```

**Запити контейнера (CSS Contain Spec L3):**

Запити контейнера застосовують стилі на основі розміру контейнера, а не видимовікна. Це дозволяє справжню адаптивність на рівні компонента.

```css
@container (min-width: 500px) {
  .card {
    display: grid;
    grid-template-columns: 1fr 1fr;
  }
}
```

**Перевага:** Компоненти масштабуються незалежно від видимовікна, дозволяючи повторно використовуваним адаптивним компонентам.

### 3.4 Системи інтервалів та масштабування

Професійні проекти використовують послідовні шкали інтервалів, як правило, на основі базової одиниці (напр., 4px, 8px).

```css
:root {
  --space-xs: 0.25rem;   /* 4px */
  --space-sm: 0.5rem;    /* 8px */
  --space-md: 1rem;      /* 16px */
  --space-lg: 1.5rem;    /* 24px */
  --space-xl: 2rem;      /* 32px */
  --space-2xl: 3rem;     /* 48px */
}
```

Шкали інтервалів поліпшують візуальну ієрархію та зменшують когнітивне навантаження для споживачів, які читають систему дизайну.

## Частина 4: Передові теми CSS

### 4.1 CSS-перетворення та анімацій

**Перетворення:**

CSS-перетворення застосовують 2D або 3D перетворення без впливу на потік документа.

```css
transform: translate(x, y) rotate(angle) scale(x, y) skew(x, y);
transform: matrix(a, b, c, d, e, f);  /* Пряма матрична форма */
```

**Координатна система перетворення:**

- `translateX/Y`: 2D переклад по осях
- `translateZ`: 3D глибина (вимагає `perspective` на предку)
- `rotateX/Y/Z`: Обертання навколо осей
- `perspective()`: Встановлює точку заникання для 3D перетворень

**Примітка продуктивності:** Перетворення запускають прискорення GPU в сучасних браузерах. Елементи з властивостями `transform` сприяють окремим шарам композиторів, зменшуючи витрати на перефарбування.

**Анімацій:**

CSS-анімації інтерполюють значення властивостей з часом.

```css
@keyframes slide-in {
  0% {
    transform: translateX(-100%);
    opacity: 0;
  }
  100% {
    transform: translateX(0);
    opacity: 1;
  }
}

.element {
  animation: slide-in 500ms ease-out forwards;
}
```

**Функції пом'якшення:**

- `linear`: Постійна швидкість
- `ease-in`: Повільний початок, швидкий кінець (прискорення)
- `ease-out`: Швидкий початок, повільний кінець (уповільнення)
- `cubic-bezier(x1, y1, x2, y2)`: Користувацька крива
- `steps(n)`: Дискретні кадри анімації

### 4.2 Утримання CSS та продуктивність

Утримання CSS обмежує розрахунки макета, фарбування та тесту удару браузера на незалежні піддерева.

```css
.card {
  contain: layout style paint;
}
```

**Значення утримання:**

- `layout`: Внутрішній макет елемента не впливає на зовнішній макет
- `style`: Каскадні обсяги (правила CSS локальні для елемента)
- `paint`: Елемент не фарбується поза межами його коробки
- `size`: Розмір елемента незалежний від вмісту (вимагає явних вимірів)

**Вплив на продуктивність:** Утримання зменшує область фарбування та перерахування від $O(n)$ глобального до $O(m)$ у контейнері. Для великих документів з багатьма незалежними компонентами утримання може поліпшити продуктивність фарбування на 50-300%.

### 4.3 CSS-змінні (користувацькі властивості)

CSS-користувацькі властивості (змінні) дозволяють динамічні таблиці стилів та тематизування.

```css
:root {
  --primary-color: #0066cc;
  --primary-dark: #004099;
}

.button {
  background-color: var(--primary-color);
  color: white;
}

.button:hover {
  background-color: var(--primary-dark);
}

/* Динамічне переозначення */
.dark-theme {
  --primary-color: #3399ff;
  --primary-dark: #0052a3;
}
```

**Каскадне наслідування:** CSS-змінні наслідуються як нормальні властивості. Дочірні елементи можуть переозначити батьківські змінні, дозволяючи тематичні переозначення та обсяги стилів.

**Інтеграція JavaScript:**

```javascript
// Прочитати змінну
const color = getComputedStyle(element).getPropertyValue('--primary-color');

// Написати змінну
element.style.setProperty('--primary-color', '#ff0000');
```

## Частина 5: Доступність та інклюзивний дизайн

### 5.1 Колір та контрастність

**WCAG 2.1 Вимоги контрастності:**

- **Рівень AA:** Текст >= 4.5:1, великий текст >= 3:1
- **Рівень AAA:** Текст >= 7:1, великий текст >= 4.5:1
- "Великий текст" = 18pt (24px) або 14pt (18.6px) жирний

**Розрахунок коефіцієнта контрастності:**

Дана відносна світлість $L_1$ та $L_2$ (де $L_1 \geq L_2$):

$$\text{Коефіцієнт контрастності} = \frac{L_1 + 0.05}{L_2 + 0.05}$$

Відносна світлість: $L = 0.2126 \cdot R + 0.7152 \cdot G + 0.0722 \cdot B$ (де RGB лінеаризовано від sRGB)

**Доступність для дальтоніків:**

- Дейтеранопія (червоно-зелена сліпота): ~1% чоловіків
- Протанопія (червоно-зелена сліпота): ~0.5% чоловіків
- Тританопія (сіньо-жовта сліпота): <0.01% населення

**Рисунок дизайну:** Ніколи не використовуйте колір самостійно для передачі інформації. Поєднуйте з узорами, значками або текстовими мітками.

### 5.2 Управління фокусом та навігація з клавіатури

**Індикатори фокусу:**

```css
:focus {
  outline: 3px solid #0066cc;
  outline-offset: 2px;  /* Візуальне розділення */
}

:focus-visible {
  /* Показати контур тільки для фокусу клавіатури, не мишки */
  outline: 3px solid #0066cc;
}
```

**Порядок вкладок:**

Атрибут `tabindex` контролює порядок вкладок:
- `tabindex="0"`: Бере участь у природному порядку вкладок
- `tabindex="-1"`: Фокусуємо, але не у порядку вкладок (корисно для фокусу JS)
- `tabindex > 0`: Підвищений порядок вкладок (уникайте; створює тягар обслуговування)

**Пропустити посилання:**

```html
<a href="#main" class="skip-link">Перейти до основного вмісту</a>
<main id="main" tabindex="-1">
  <!-- Основний вміст -->
</main>
```

Пропустити посилання приховані за замовчуванням, відкриті на фокусі:

```css
.skip-link {
  position: absolute;
  left: -9999px;
}

.skip-link:focus {
  left: 0;
}
```

### 5.3 Розмір тексту та читаність

**Стандарти розміру шрифту:**

- **Текст тіла:** 16px мінімум (WCAG 2.1)
- **Ієрархія заголовків:** H1 > H2 > H3 з послідовними коефіцієнтами (як правило, 1.5:1 або золоте співвідношення ≈ 1.618:1)
- **Довжина лінії:** 50-75 символів оптимальні для читаності (типографічний захід)

**Висота лінії та інтервал:**

```css
body {
  font-size: 16px;
  line-height: 1.5;  /* 24px фізична висота */
  letter-spacing: 0;  /* Моноспар: 0.12em типовий */
  word-spacing: 0;    /* За замовчуванням: ширина простору */
}
```

**Переозначення переваги користувача:**

```css
@media (prefers-reduced-motion: reduce) {
  * {
    animation-duration: 0.01ms !important;
    transition-duration: 0.01ms !important;
  }
}

@media (prefers-color-scheme: dark) {
  :root {
    --bg: #1a1a1a;
    --fg: #ffffff;
  }
}
```

## Частина 6: Оптимізація продуктивності

### 6.1 Конвеєр рендерингу та заїдання

Конвеєр рендерингу браузера обробляє CSS-зміни через кілька етапів:

1. **Розрахунок стилю:** $O(n)$ де $n$ = відповідні селектори
2. **Макет:** $O(m)$ де $m$ = мають на увазі елементи (залежить від BFC)
3. **Фарбування:** Генерувати команди малювання
4. **Композит:** Об'єднувати шари на GPU

**Причини заїдання:**

Довгі (>16мс) кадри спричиняють розпадання анімацій 60fps. Типові причини:
- Синхронні цикли читання-запису DOM (упорання макета)
- Дорогі селектори (глибокі комбінатори нащадків)
- Примусові макети через `offsetHeight`, `scrollTop`, `getComputedStyle()`

**Приклад упорання макета:**

```javascript
// ❌ ПОГАНО: Спричиняє 3 переобчислення макета (1000x)
for (let i = 0; i < 1000; i++) {
  elem.style.width = elem.offsetWidth + 10 + 'px';  /* Прочитати потім написати */
}

// ✅ ДОБРЕ: Одиночний розрахунок макета
const width = elem.offsetWidth;
for (let i = 0; i < 1000; i++) {
  elem.style.width = (width + (i + 1) * 10) + 'px';
}
```

### 6.2 CSS-in-JS та критичний CSS

**Критичний CSS:** Вбудовувати мінімальний CSS необхідний для вмісту вище згину, відстрочуючи CSS нижче згину.

```html
<head>
  <style>
    /* Критичний CSS для заголовка, героя, вмісту вище згину */
    html, body { margin: 0; }
    .header { /* ... */ }
  </style>
</head>
<body>
  <!-- Завантажити решту CSS асинхронно -->
  <link rel="preload" href="styles.css" as="style" onload="this.onload=null;this.rel='stylesheet'">
  <noscript><link rel="stylesheet" href="styles.css"></noscript>
</body>
```

**Компроміси CSS-in-JS:**

| Підхід | Переваги | Недоліки |
|--------|----------|---------|
| Статичні файли CSS | Нульова вартість часу виконання; кеш браузера | Більший початковий пакет; дублювання |
| CSS-in-JS (emotion, styled-components) | Обсяг компонента; усунення мертвого коду | Аналіз часу виконання; більший пакет JS; складніше налагодження |
| CSS модулі | Обсяг; інтеграція webpack | Підтримка назви класу; залежність збірки |

### 6.3 Стратегія завантаження шрифту

Завантаження шрифту блокує рендеринг (FOUT = спалах неперевіреного тексту; FOIT = спалах невидимого тексту).

**Стратегії оптимізації:**

1. **font-display: swap:** Використовуйте замінник негайно, помінляйте при готівці (найшвидше сприйняте)
2. **font-display: optional:** Використовуйте замінник, якщо не кешовано (краще для не критичних шрифтів)
3. **font-display: auto:** Браузер за замовчуванням (як правило, FOIT)
4. **Preload:** `<link rel="preload" href="font.woff2" as="font" type="font/woff2">`

```css
@font-face {
  font-family: 'CustomFont';
  src: url('custom.woff2') format('woff2');
  font-display: swap;
  font-weight: 400;
  font-style: normal;
}
```

### 6.4 Вимірювання та профілювання

**Web Vitals (Core Web Vitals):**

1. **LCP (Найбільший контентний фарб):** Час рендерингу найбільшого видимого елемента
   - Ціль: < 2.5s
   - Виміряно через `PerformanceObserver`

2. **FID (Перша затримка вводу):** Затримка від вводу користувача до виконання обробника
   - Ціль: < 100мс
   - Викликано основною блокуванням потоку (виконання JS)

3. **CLS (Кумулятивна зміна макета):** Візуальна нестійкість під час завантаження
   - Ціль: < 0.1
   - Викликано невідмірними зображеннями, оголошеннями, вбудовуваннями

```javascript
// Виміряти LCP
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log('LCP:', entry.startTime);
  }
});
observer.observe({ entryTypes: ['largest-contentful-paint'] });

// Виміряти CLS
let clsValue = 0;
const clsObserver = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (!entry.hadRecentInput) {  /* Виключити користувацькі зміни */
      clsValue += entry.value;
    }
  }
});
clsObserver.observe({ entryTypes: ['layout-shift'] });
```

## Частина 8: Питання для старших інтерв'ю

### Концептуальні питання

**Q1: Поясніть різницю між `margin-top` згортанням та `padding-top`. Коли відбувається згортання маржи і чому доповнення не згортається?**

**Структура відповіді:**
- Згортання маржи — це функція BFC; тільки вертикальні маржі між рівноправниками блока згортаються
- Згортання дозволяє послідовний інтервал незалежно від дочірніх маржи (прогресивне покращення)
- Доповнення ніколи не згортається (це внутрішній простір, а не між елементами)
- Усунення згортання маржи: `overflow: hidden`, `display: flex`, `display: grid`, межи, доповнення

**Q2: Чому `z-index` часто ненадійний і яке справжнє рішення?**

**Структура відповіді:**
- `z-index` працює тільки в рамках рівноправних контекстів стекування
- Сучасний CSS створює неявні контексти стекування (непрозорість, перетворення, фільтр)
- Рішення: Уникайте ієрархії `z-index`; використовуйте явний контекст стекування на відомому предку
- Використовуйте CSS-змінні для явного шарування, якщо потрібно

**Q3: У вас є вузьке місце продуктивності у складному інтерфейсі з 500+ елементами. Етапи фарбування та растризації повільні. Які властивості CSS допомагають і чому?**

**Структура відповіді:**
- `will-change: transform, opacity` (сприяє шару композитора)
- `contain: layout paint` (обмежує область фарбування)
- `backface-visibility: hidden` (оптимізація кеша CPU)
- Уникайте запуску перефарбування через властивості, які не впливають на межи вмісту

### Практичні сценарії

**Q4: Розробіть адаптивну сітку, яка автоматично адаптується до ширини контейнера без запитів медіа. Як би ви обробляли пропуски та вирівнювання?**

**Структура відповіді:**
```css
.grid {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(250px, 1fr));
  gap: clamp(1rem, 5vw, 2rem);  /* Адаптивна розриву */
  align-items: start;  /* Запобігати розтягуванню для елементів змінної висоти */
}
```

**Q5: Реалізуйте темний режим, який поважає перевагу користувача, але дозволяє ручне переозначення. Який рисунок CSS мінімізує проблеми специфічності?**

**Структура відповіді:**
- Використовуйте CSS-змінні на `:root` рівні
- Переозначити за допомогою `[data-theme="dark"]` або `.dark-theme` класу
- Використовуйте запит медіа `prefers-color-scheme` як базовий план
- JavaScript переключає атрибут `data-theme` для ручного переозначення

## Частина 9: Ключові висновки

1. **Семантичний HTML** не є необов'язковим—він безпосередньо впливає на доступність, SEO та оптимізацію браузера
2. **Специфічність CSS** — це математична модель; розуміння запобігає каскадам хаків
3. **Режими макета** (блок, flex, сітка) принципово відрізняються; неправильний вибір спричиняє упорання макета
4. **Продуктивність** вимагає розуміння конвеєру рендерингу браузера—властивості перетворення дешеві, переобчислення макета дорогі
5. **Доступність** — це вимога дизайну, а не звичайна робота; ARIA — це останній засіб, а не перший вибір
6. **Адаптивний дизайн** еволюціонував від запитів медіа до запитів контейнера та систем на основі токенів
7. **Архітектура CSS** масштабується через схеми найменування та утримання, а не вкладення препроцесора CSS
8. **Виробничі системи** вимагають моніторингу (Web Vitals) та профілювання, щоб запобігти регресії продуктивності

## Висновок

HTML та CSS утворюють оманливо складний фундамент веб-розробки. Цей посібник вийшов за межи синтаксису та візуальних ефектів, щоб дослідити математичні принципи, механіку конвеєру рендерингу та архітектурні патерни, які розрізняють старшу інженерію від новатора.

Майстерність вимагає розуміння не тільки *що* ці технології роблять, але *чому* вони працюють так—від математики контексту стекування до стратегій завантаження шрифтів до побудови дерева доступності. Виробнича інженерія вимагає усвідомлення компромісів: коли використовувати flexbox vs. сітку, коли ARIA доречна, як утримання CSS впливає на область рендерингу.

Коли ви рухаєтеся вперед, зосередьтесь на:
- **Теоретичній глибині:** Розуміти каскад CSS і специфічність як формальну систему
- **Поінформованості щодо продуктивності:** Профіль та виміри; уникайте припущень про оптимізацію
- **Доступність спочатку:** Розробіть включаючий досвід, потім додайте удосконалення
- **Архітектурні патерни:** Масштабуйте CSS через системи, а не хаки
- **Внутрішні особливості браузера:** Знайте конвеєр рендерингу; експлуатуйте його ефективно
